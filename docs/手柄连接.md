## 编 padd

`scripts/build.sh` 只编 `robotd` / `robotctl`，`padd` 单独来。它是这条线上唯一带 C 依赖的
（`gilrs` → `libudev`），本机没有 arm64 头文件，造一个最小 sysroot：

```bash
# 1) 板子上取包（版本和板子一致）
ssh root@192.168.3.10 'cd /tmp && apt-get download libudev-dev'

# 2) 主机上解开
mkdir -p /home/ai/arm64-sysroot
dpkg-deb -x libudev-dev_*_arm64.deb /home/ai/arm64-sysroot

# 3) 板子的 libudev.so.1 也要拿过来 —— dev 包里只有一个悬空软链
scp root@192.168.3.10:/usr/lib/aarch64-linux-gnu/libudev.so.1.7.10 \
    /home/ai/arm64-sysroot/usr/lib/aarch64-linux-gnu/
ln -sf libudev.so.1.7.10 /home/ai/arm64-sysroot/usr/lib/aarch64-linux-gnu/libudev.so.1

export PKG_CONFIG_SYSROOT_DIR=/home/ai/arm64-sysroot
export PKG_CONFIG_PATH=/home/ai/arm64-sysroot/usr/lib/aarch64-linux-gnu/pkgconfig
export PKG_CONFIG_ALLOW_CROSS=1
export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=aarch64-linux-gnu-gcc
cd microduck && cargo build --release --locked --target aarch64-unknown-linux-gnu -p padd

# 4) 放进 out/arm64/bin —— build.sh 不管 padd，而 deploy.py 只搬 out/arm64
install -m755 target/aarch64-unknown-linux-gnu/release/padd ../out/arm64/bin/
```

链接时警告 `libcap.so.2 … not found`：无害，板子上有，运行时解析。

## 跑 padd

**2026-10-17 起由 systemd 管，开机自启。** 单元在仓里
`microduck/padd/systemd/padd-runtime.service`，板上装成 `/etc/systemd/system/padd.service`：

```bash
systemctl status padd.service
journalctl -u padd.service -f        # 日志
systemctl restart padd.service
```

单元里写死了 `--socket /home/duck/workspace/microduck-hd1910m/local/robotd.sock`
（padd 默认找 `/run/robotd.sock`，我们这套 runtime 不用那个路径）。
`duck` 在 `input` 组，读 `/dev/input/event4` 不要 root。
没手柄时它什么都不发、robotd 的 deadman 自己压着，所以常驻是安全的。

手工调试时可以前台跑：

```bash
cd /home/duck/workspace/microduck-hd1910m
su duck -s /bin/bash -c "./out/arm64/bin/padd --socket ./local/robotd.sock"
```

成功的判据：日志出现 `pad connected — driving`。

## 按键

绑定来自 `/etc/robot/robotd.toml` 的 `[pad]`；板上没这文件，走默认映射。
`gilrs` 不认识这支手柄的 UUID（`05000000-3735-0000-0e10-00001b010000`），日志会警告
`No mapping found … Default mapping will be used`，但实测键位是对的。

| 键 | 动作 | 这台鸭子有吗 |
|---|---|---|
| Start 点按（第一次） | `robot.init`：扭矩上电 + 2 秒斜坡回站姿并保持，**策略还不接管** | ✅ |
| Start 点按（第二次） | 启动策略，鸭子开始走 | ✅ |
| Start 点按（之后） | 开 / 关策略（关＝回 home，**仍然有扭矩**） | ✅ |
| 左摇杆 | 前后走 / 左右平移 | — |
| 右摇杆 | 转向 | — |
| **X** | 头模式（摇杆摆头，行进速度归零） | ✅ |
| **B** | 身体姿态（设计上是倾 / 蹲） | ❌ 见下方说明，实际只等于"停车保持站姿" |
| 十字键 ↑ 点按 | 循环摇杆模式：移动 → 控头 → 身体姿态 → 移动 | — |
| 十字键 ↓ 点按 | `sit_toggle` | ❌ 这台 `sitstand = none` |
| 十字键 ← 按住 2 秒 | 清舵机锁存故障（全关节断电，之后要重新按 Start 起身） | — |
| A | `ground_pick` | ✅ |
| **Y** | `roulade`（配置里这个键叫 `x`；按住会持续重发） | ✅ 要等站好（Ready）才生效 |
| LB / RB | `kick_left` / `kick_right` | ❌ slot 是 `none`，按了回 `no skill named …` |
| RT / LT | 张嘴 / 叫声（RT 触发 quack） | — |
| **Select 松开（短按）** | **卸扭矩急停**（`robot.relax`），鸭子当场瘫软 | — |
| **Select 按住 2 秒** | 坐下 + **关机** | ⚠️ 别误按，和短按只差按住时长 |

**X 和 Y 是反的，不是写错**：gilrs 认不出这支手柄的 UUID，走默认映射、按 evdev 码位编号
（North = `BTN_X` = 物理 X，West = `BTN_Y` = 物理 Y）。所以代码里的 North / 头模式是实体 **X**，
West / 配置里的 `x`（`roulade`）是实体 **Y**。有正规映射的手柄才是"Y 头模式、X 翻滚"，
官方文档和 kissqy 的 Xbox 桥都是那种叫法。

**身体姿态在这台上是空的**：`padd` 发的 z / pitch / roll 到了 `robotd` 会被清零
（`control.rs` 里 `if reference { effective.body = Default::default() }`），而且这台
`stand = "none"`、没有站立网络。按 B 的实际效果只有"速度归零、保持站姿"，看不到倾或蹲。

**映射 2026-10-29 按官方 `padd` 改了**（官方说明见 [OFFICIAL-GAMEPAD.zh-CN.md](OFFICIAL-GAMEPAD.zh-CN.md)）：Start 改成"第一次起身、第二次走"，
卸力从"Start 按住 2 秒"挪到"Select 松开"，十字键 ↑ 改切摇杆模式（原来的
"↑ 按住 3 秒切行走/轮式"已去掉，这台没有轮式包）。

**2026-10-30 23:07 已上板复测。** 之前板上跑的还是 10-28 23:42 编的旧二进制（横幅是
`Start taps the policy (hold 2s relaxes)`），代码改了没搬上去。当天重新交叉编译
（`target/aarch64-unknown-linux-gnu/release/padd`，sha256 `7386bc7c…c2aa30`），
旧版备份成 `out/arm64/bin/padd.bak-20261028`。重启后横幅确认：

```
driving — Start once stands up, Start again toggles the policy, Y head mode, B body pose,
A ground pick, LB/RB kicks, DPad-Down sit, triggers mouth, DPad-Up cycles stick mode,
DPad-Left (2s) clear fault, Select (release) torque off, Select (2s) sit and shutdown
```

**以后改 padd 记得手抄一遍这行横幅**：`scripts/build.sh` 不管 padd，很容易出现
"代码改了、板上还是旧的"。

## 坑

1. **板子电源键一按就关机，不是故障。** 日志是
   `systemd-logind: Power key pressed short.` → `Powering off...`。
   两次都发生在 `roulade` 开始后几秒 —— 鸭子翻身碰到了板子电源键。查关机先看这一行。
2. **AIC8800 蓝牙会彻底卡死，只能重启板子。**
   2026-10-17 三次：一次 `roulade` 之后、两次手柄闲置掉线之后。

   **掉线那一刻就聋了，不是板子去连的时候才坏。** 15:13 手柄掉线 → 15:32 手柄开机主动
   呼板子 → 无响应；直到 15:33 有人敲 `connect`，才第一次暴露成 `0x0408 tx timeout`。
   实测那会儿：主机 `TX bytes` 照涨（命令确实发出去了），但 `ttyS1` 的中断计数
   241593 **一个字节都不动** —— 物理链路通，芯片不吭声。同一颗芯片的 WiFi 半边全程正常
   （这台 SSH 就走在它上面），所以不是整颗芯片断电或复位。

   软恢复全试过，**一个都不管用**（别浪费时间）：

   | 试的 | 结果 |
   |---|---|
   | `bluetoothctl power off/on` | `Failed to set power off` |
   | `systemctl restart bluetooth` | `hci0` 变 `00:00:00:00:00:00`，照样超时 |
   | `hciconfig hci0 reset` | `Connection timed out` |
   | `/sys/bus/platform/drivers/aic_bt/{unbind,bind}` | 设备本来就没绑（`refcnt 0`），没反应 |
   | `rfkill block/unblock 0` | 芯片真的断电重上了（`BT_RFKILL: bt shut off power` → `bt turn on power`），HCI 还是不答 |
   | `modprobe -r hci_uart` | `in use`，hci0 钉住模块，卸不掉 |
   | `systemctl restart aic-bluetooth` | 硬复位 + 重新 attach，**attach 后第一条命令（`0x1003`）照样超时**，`hci0` 变 `DOWN` |

   **为什么只有重启有效**：蓝牙固件是开机时由 AIC 驱动栈一次性灌进芯片的，
   用户态没有任何重灌入口。上面每一条都只是「重新 attach」或「断电」，
   芯片里跑的还是那份已经挂死的固件 —— 所以全都无效。

   **为什么会挂**：没有证据。最可能的是掉线后进低功耗、唤醒握手失步
   （GPIO 上是 `bt_default_wake` 高、`bt_default_wake_host` 低，看不出异常）。
   AIC8800 没有芯片侧日志，拿不到直接证据。

   重启掉扭矩、鸭子会瘫；重启后手柄自动回连，`padd` 要手工重起。

   **下次卡死先抓现场再重启**（这组值留作对比）：
   `grep ttyS1 /proc/interrupts`（发了命令却不涨，就是芯片聋了）、
   `hciconfig hci0 | tail -2`、`grep -E "gpio-(11|12|17|77) " /sys/kernel/debug/gpio`。

   板上有 **`bt-watch`**（`tools/bt-watch/`，systemd 常驻）自动做这件事：
   每 5 秒记一行（ttyS1 中断数、四根控制线、js 设备数、hci0 收发计数），
   环形缓冲留最近一小时；手柄掉线或出现新的 `tx timeout` 时，把缓冲 + dmesg 尾部
   落到 `/var/log/bt-watch/`。下次卡死直接看那里，不用再手工抓。
3. ~~重启后 `padd` 不会自己起来~~ —— 2026-10-17 起有 `padd.service`，开机自启。
4. **手柄闲置会自动关机**，是 GameSir 固件自己的省电，板子这边改不了。
   影响不大：`padd` 打 `pad gone — sending nothing`，`robotd` 的 deadman 把速度归零，
   鸭子停住站着；策略状态保留，手柄重新开机自动回连后不用再按 Start。
   **2026-10-17 14:52 实测**：闲置关机 → 2 分钟后开机 → 14:54 自动回连，
   `hci0` 一直 `UP RUNNING`，蓝牙没卡死。所以自动关机本身无害，
   卡死是偶发的（今天两次卡死都在掉线之后，但不是每次掉线都卡）。
