# 语音交互方案（2026-11-02 设计，2026-11-07 实现第 1–2 阶段）

目标：对着鸭子说话，它能**听懂指令去做动作**，也能回答**"你能看到什么"**——拍照、
描述、说出来。

麦克风和喇叭的链路已经通了（见 [麦克风与录音.md](麦克风与录音.md)），摄像头和 mediad
也已经部署（见 [摄像头接入.md](摄像头接入.md)）。缺的是中间那一层。

## 架构

```
麦克风（48 kHz 立体声，只有右声道有声）
   ↓  取右声道 → 16 kHz 单声道
VAD 分句（Silero，常驻几乎不耗 CPU）
   ↓  一句完整的语音
ASR（本地 sherpa-onnx 离线中文，SenseVoice）
   ↓  文本
意图分流 ──┬─ 指令（前进 / 停 / 坐下 / 叫一声）→ RobotMove / RobotDo / RobotSound
           │                                    全本地，< 1 秒
           └─ 问题（"你能看到什么"）→ 抓一帧 + 云端视觉模型 → 一句话 → TTS → 喇叭
                                                3–5 秒
```

IPC 已经有了，不用改 robotd：`RobotMove`（连续速度）、`RobotDo`（一次性技能 / 坐站切换）、
`RobotSound`、`RobotStop`、`RobotInit`、`RobotRelax`（见 `duck-ipc-proto` 的 `Call`）。

## 组件选型

| 部件 | 选型 | 理由 |
|---|---|---|
| 听 | sherpa-onnx 离线 SenseVoice-small（int8，239 MB）+ Silero VAD | 离线、全本地、带标点；同样的提示音 CER 7.8%，比最初选的流式 zipformer 14M（12.5%）低近一半，见下节实测 |
| 看 | **云端**多模态模型 | 板子 NPU 约 1 TOPS，跑任何像样的中文视觉模型都是几秒一张且效果差。这是唯一实在的选择 |
| 说 | Piper 中文（本地，~60 MB） | ARM 上实时、自然度够；`sounds` crate 的合成音只能做提示音 |
| 编排 | 新 crate，bin `duck-ear` | 复用现有 IPC，不碰 robotd |
| 取帧 | `mediad` 加一个 `GET /snapshot.jpg` | 摄像头被 mediad 独占，但内部已有 `Frames::next_frame()`（"只取最新一帧"的机制，探测分支在用），加路由是小改动，不用停流 |

## 板子的容量（2026-11-02 实测）

```
CPU 4×A55 @1.8 GHz   负载 0.93（robotd 19% + mediad 3.7%）
内存 1967 MB         已用 281 MB，可用 1685 MB
温度 67 °C / 63 °C
硬盘 57 G，剩 53 G
外网通（github / huggingface 都 200）
```

预算：现有 300–500 MB + ASR 100–300 MB + TTS 80–150 MB ≈ 700 MB–1 GB、峰值约 2.5 个核。
**内存和算力够用。**

## 三条硬约束

1. **视觉必须上云。** 本地跑不动，也别试——NPU 只有约 1 TOPS。
2. **温度是真正的瓶颈，不是算力。** 这块板子散热很弱：mediad 曾经因为 MPP 走软件转换
   把 CPU 压到 408 MHz、温度 97 °C、帧率掉到 8 fps。空载已经 67 °C，再叠一路持续推理
   很可能降频，表现是"识别越来越慢"。
3. **不能常开 ASR。** 降温靠"平时不开"：命令词用关键词检测模型（几 MB，开销 1/10），
   真要理解整句才拉起 ASR；或者按键 / 唤醒词再开。

## 明天的第一件事：基准测量

在板上跑一段流式 ASR，同时盯 CPU 频率和温度，判断会不会降频。判定标准：

- 实时系数（RTF = 处理耗时 / 音频时长）< 0.5 才有余量；
- 连续跑 2 分钟，`scaling_cur_freq` 不低于 1.4 GHz（不降频）；
- 温度不超过 85 °C；
- RSS 增长后稳定，不持续上涨。

量法：

```bash
# 一边跑 ASR，一边每 2 秒采一次
while true; do
  echo "$(date +%T) $(cat /sys/class/thermal/thermal_zone0/temp) \
        $(cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq) \
        $(grep VmRSS /proc/<pid>/status)"
  sleep 2
done
```

结果决定指令层用**关键词检测**还是**完整 ASR**——这是唯一还悬着的架构选择。

### 实测结果（2026-11-07）

模型：`sherpa-onnx-streaming-zipformer-zh-14M-2023-02-23`（int8 编码器 21 MB / 解码器 7.5 MB /
joiner 96 KB / tokens 47 KB），sherpa-onnx 2.0.1 + numpy 2.5.4，Python 3.12.16（uv 装的独立
venv，板上没动系统 Python）。测速脚本留在板上 `~/voice-bench/bench_asr.py`（满速压测）和
`bench_rt.py`（按麦克风速率实时喂 2 分钟）。

```
满速压测（2 线程）  relax.wav 2.3 s × 8
  wall RTF  0.251   cpu RTF 0.861（3.4 核忙）
实时喂 120 s（2 线程）  decode 占墙钟 22%，温度稳态 72–73 °C，1800 MHz
实时喂 60 s（1 线程）   decode 占墙钟 26%，温度 67–69 °C，1800 MHz，RSS 117 MB 恒定
```

结论：

- **三条判定线全部有富余**：RTF 0.25 对 0.5，主频全程 1800 MHz 对 1.4 GHz，温度 73 °C 对 85 °C。
- **`num_threads=1` 是最优点。** 2 线程墙钟只快一点点（0.22 → 0.26），CPU 却贵 2.5 倍
  （0.86 → 0.26 核）——这个模型太小，ONNX Runtime 的多线程自旋开销比并行收益大。单线程
  给 50 Hz 控制环留 3/4 个核。
- **常开 ASR 可以不做了关键词检测。** 持续解码约占墙钟 1/4，代价是 ~0.26 个核、稳态 68 °C；
  离文档担心的"降频"还远。先用完整 ASR 换识别质量，真过热再退 KWS。
- 内存 117 MB，不随运行时长增长。
- 已知噪声：测速脚本把 48 kHz 提示音直接抽点降到 16 kHz（没有抗混叠），"伺服故障，已复位"
  这类句子的识别会被这一步拖坏；真实链路要接到 16 kHz 采集后的数据，或做正经重采样。
  这不影响上面的负载数字。

### 换模型：流式 vs 离线（2026-11-07 晚）

真机说话时 14M 流式模型把「叫一声」听成「叫医生」「下一声」——同音，不同字。热词偏置
（beam search + `cjkchar` 热词，分数 3.0）能救回一部分，但代价是常驻 CPU 从 1/4 核涨到
**1/3 核**（beam search 比 greedy 贵得多），而且只堵同音，不解决整体准确率。于是把板上
能跑的候选都量了一遍，用同一批 11 条提示音（`/var/lib/robot/prompts`）、同一套 24 抽头
抗混叠降采样、同一个 CER 定义：

| 模型 | CER | 解码 RTF（2 线程） | RSS | 加载 |
|---|---|---|---|---|
| 流式 zipformer 14M-2023 | 12.5 % | 0.21（常开） | 108 MB | 15 s |
| 流式 zipformer zh-int8-2025-06-30 | 10.9 % | 0.70（常开，1 线程） | ~200 MB | — |
| **SenseVoice-small int8-2024-07-17** | **7.8 %** | 0.42（每句） | 366 MB | 11.5 s |
| paraformer-zh int8-2023-09-14 | 7.8 % | 0.46（每句） | ~400 MB | 10.5 s |

两个离线模型打平，SenseVoice 单句更快、带标点，选它。剩下的 5 个错字全是
`伺服 → 四伏/四幅`、`噶 → 嘎`，都不在指令词表里。

**NPU 走不通。** 板上有 `/usr/lib/librknnrt.so` 2.3.2、内核 `CONFIG_ROCKCHIP_RKNPU=y`，
但没有 `/dev/rknpu`（`/dev/dri` 只有显示和 panfrost），而且我们随二进制带的
sherpa-onnx 1.12.9 预编译库是纯 CPU 版。RK3566 的 NPU 版模型包（391 MB）因此作废。

**架构随之改成 VAD 分句 + 离线识别。** 离线模型一次吃一整句，Silero VAD 负责断句
（0.5 s 静音后交付一段）。常态只跑 VAD，几乎不占 CPU；说话时才解一句。实测一句 1.2 s
的指令：VAD 等 0.5 s + 解码 0.5 s ≈ 说完 1 秒后动作。代价是没有边说边出的部分结果，
也没有热词——这两样是流式模型的能力，`intent` 层不受影响。

板子 2 GB 内存。守护进程实测常驻 RSS 607 MB（Python 对照只有 366 MB，差在 ONNX Runtime
的 arena），装上后系统仍剩约 1 GB 可用；空闲 CPU ~9.5%（只剩 VAD 在跑，原流式版是 33%）。

## 分阶段

1. ~~**基准测量**~~ —— 2026-11-07 完成，见上一节。结论：完整流式 ASR 开得起，不上关键词检测。
2. **ASR + 指令控制** —— 已实现，crate `microduck/duck-ear`（设计说明见
   [microduck/docs/design/voice-control.md](../microduck/docs/design/voice-control.md)）。
   支持停、坐站切换、前进一小步、叫一声；不提供"解锁/开始"，策略仍只由手柄 Start 启动。
   2026-11-07 板上 `--dry-run` 跑通：模型加载 15 s，稳态 RSS 101 MB、65 °C、1800 MHz、
   约 1/4 个核；放 `relax.wav` 识别出「我累了休息一下」，且不命中任何指令。当天晚些时候
   换成 VAD + SenseVoice（见上节），常驻 CPU 降到接近 0，准确率 12.5 % → 7.8 %。真机动作
   （停/坐站/前进）要等手柄使能后再试。
3. **`mediad` 加 `/snapshot.jpg`**：一行路由 + JPEG 编码。
4. **TTS**：Piper 中文接进 `voice` crate（`play` 已经有了，只多一步合成）。
5. **云端视觉问答**：抓帧 → 上传 → 一句话 → TTS。需要 API key。
